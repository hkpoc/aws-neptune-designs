1. Architectural Context & Neptune Isolation Mechanics

Purging millions of vertices and edges from live multi-tenant Amazon Neptune clusters (both Provisioned and Neptune Serverless) presents three distinct operational risks: (1) Discovery Traverse Overhead, where deep graph traversals evict warm buffer-pool cache pages and spike read IOPS on production instances; (2) Write Amplification & MVCC UndoLog Growth, where unthrottled batch drop() mutations flood the primary writer's transaction queue and inflate UndoLogListSize; and (3) Serverless Auto-Scaling Cost Runaway, where unthrottled writes force Neptune Serverless clusters to scale up to their maximum NCU cap (1 to 128 NCUs).

Critical Neptune Architecture Distinction: Fast Database Clone vs. Read Replica

In Amazon Neptune, a standard Read Replica belongs to the primary DB cluster and shares the underlying distributed storage fleet. Adding a read replica cannot exist "outside the cluster." To isolate discovery compute from production without a full-copy restore by default, the Discovery Phase provisions an ephemeral Neptune Fast Database Clone (RestoreDBClusterToPointInTime with RestoreType=copy-on-write and UseLatestRestorableTime=true). Create a separate DB instance after restoration and wait for readiness. Copy-on-write initially shares unchanged storage pages; subsequent changes consume additional storage and discovery incurs compute and applicable I/O charges. Compute, cache and endpoints are independent, but zero production impact and fixed provisioning times are not guaranteed. Benchmark actual provisioning and production latency. CopyTagsToSnapshot is not a restore parameter and does not enable cloning.

4. End-to-End Execution Sequence Diagram

The sequence diagram below illustrates the lifecycle of a single weekly tenant run, highlighting how Discovery and Execution are strictly decoupled via S3 manifests and SQS chunk pointers, and how the ephemeral clone is destroyed immediately upon discovery completion to minimize AWS Neptune instance/NCU hours.

Figure 2: Sequence Lifecycle — Decoupled Clone Discovery, Immediate Clone Teardown, and Mode-Aware Health-Checked Execution
Runtime lifecycle contract (authoritative over the simplified diagram)
  1. Acquire a fenced per-source-cluster and per-run lease; paginate tenant configuration and freeze rule version and cutoff.
  2. Restore clone with a deterministic unique identifier, ownership tags and explicit network/IAM settings. Poll DescribeDBClusters until ready; CreateDBInstance and poll DescribeDBInstances until available. Verify endpoint, clone group and authentication.
  3. Run discovery via Batch SubmitJob.sync. Checkpoint deterministic S3 chunks; seal manifest only after full discovery, reconcile pointers with ledger. Never start an executor on an incomplete manifest.
  4. On success or failure, delete only the verified clone instance, wait for deletion, then delete clone cluster with SkipFinalSnapshot=true and wait. Retry transient errors; persist cleanup status. A separate reaper handles aborted executions.
  5. Run edge phase then vertex phase, with a ledger-confirmed barrier. Acknowledge SQS only after conditional ledger completion. Respect maintenance window, return PAUSED when incomplete; release lease safely.
  6. Reconcile every expected chunk, including DLQ and uncertain outcomes. Only mark COMPLETED after all required outcomes and cleanup are resolved.

5. Adaptive Database Health & Backpressure Control (Provisioned & Serverless)

Deleting vertices in Amazon Neptune requires removing both the vertex properties and all incident in/out edges. Large unthrottled deletes cause lock contention (ConcurrentModificationException) and grow the MVCC UndoLogListSize, which degrades read latency for production clients. Furthermore, on Neptune Serverless, relying solely on CPUUtilization < 45% causes an auto-scaling feedback trap: Neptune Serverless continuously scales up NCUs (up to 128 NCUs) to absorb the purge load, keeping CPU artificially low while silently driving your NCU-second billing to MaxCapacity.

Neptune Serverless Discovery Clone & Execution Cost Guardrails
  • Discovery Clone Compute Strategy: Even when a tenant's production cluster runs on Neptune Serverless, you can attach either a fixed Provisioned instance (e.g., db.r6g.xlarge) for a hard hourly price ceiling during full-throttle scans, or a capped db.serverless instance configured with MinCapacity=2.0, MaxCapacity=16.0 so the discovery scan never scales beyond 16 NCUs.
  • Execution NCU Soft Cap (MaxPurgeNcuThreshold): On the production Serverless Writer, the Execution Worker uses a per-writer NCU soft throttle threshold (e.g., 12 NCUs on a cluster whose daytime MaxCapacity is 64 NCUs). Once ServerlessDatabaseCapacity reaches MaxPurgeNcuThreshold, the AIMD controller shifts into the Yellow (Throttle) state to reduce purge load; application traffic may still increase NCU allocation.
  • Small Buffer-Cache Protection: Because 1 NCU ≈ 2 GB RAM, a Serverless instance idling at 2 NCUs overnight has ~4 GiB of total instance memory, not exclusively buffer cache. If BufferCacheHitRatio dips below 95%, the worker caps sub-batch sizes at 125 IDs (pause below 85%) to prevent storage I/O thrashing.

// Implementation pseudocode: one controller per source writer; values come from ThrottlePolicy.
// CloudWatch ~60s, live queue 10–30s, batch latency/conflicts every batch.
writer = resolveCurrentWriter(sourceClusterId); // DescribeDBClusters / IsClusterWriter
health = readWriterMetrics(writer, clusterId);  // AWS/Neptune, correct dimensions/statistics
policy = loadThrottlePolicy(tenantId);
status = evaluateCpuQueueUndoConflictsAndAppSlo(health, policy);
if (health.isMissingOrStale() || writerChanged()) status = RED;
if (writer.isServerless()) {
    status = maxSeverity(status, evaluateNcuCapacityAndUtilization(health, policy));
    status = maxSeverity(status, evaluateCacheHealth(health, policy));
}
// RED wins over YELLOW; never issue new writes in RED.
if (status == RED) {
    pauseNewWrites(); // allow in-flight transactions to finish safely
    heartbeatOrCheckpointAndReleaseSqsLease();
    waitForFreshHealthySamples();
} else if (status == YELLOW) {
    rate = max(policy.MinRate, rate / 2);
} else if (consecutiveFreshGreenSamples >= policy.GreenSamplesToIncrease) {
    rate = min(policy.MaxRate, rate + policy.RateIncreaseStep);
}
// Adjust one control variable (rate) per interval; coordinate globally per writer.
batchSize = min(policy.MaxBatchSize, degreeAwareBatchLimit());
if (writer.isServerless() && health.cacheHitRatio < policy.MinBufferCacheHitRatioPct)
    batchSize = min(batchSize, 125); // apply after adaptation
// Honor maintenance window, cluster-wide concurrency lease and retry budget.
// Missing telemetry, failover, or breached application SLO stops new writes.
Handling the Day-1 Multi-Million Backlog vs. Ongoing Weekly Runs

Because Discovery writes immutable manifest chunks to S3 and enqueues pointers into SQS (with a 14-day retention period), you can safely configure a Max Execution Window per tenant in DynamoDB (e.g., 6 hours during Sunday off-peak). If the Day-1 backlog discovers 25 million records and only 8 million are purged within the Sunday off-peak window while maintaining CPUUtilization < 50% (and, for Serverless, targeting ServerlessDatabaseCapacity ≤ 12 NCUs), the worker checkpoints and exits when the window closes. Mark the run PAUSED, not COMPLETED. Remaining candidates are durable in S3 and the chunk ledger; SQS pointers may expire after 14 days and must be reconstructable. Resume on subsequent nights, revalidating every candidate against live production.

Live-data correctness and resumability

The clone is a point-in-time candidate source, not authority to delete. In the production mutation transaction, recheck tenant, label, timestamp, frozen cutoff and immutable identity/version when IDs can be reused. For explicit expiry properties compare expiry directly against the run cutoff; for creation timestamps subtract retention once. Vertex deletion removes incident edges; enforce the business relationship policy (orphan-only example below). Edges-first ordering requires a phase barrier, not merely FIFO queues.

// Illustrative Gremlin text: serialize IDs/values safely or use driver bytecode.
// Numeric cutoff below is an example; use the frozen run cutoff.
g.E('edge-1','edge-2').hasLabel('SESSION_EVENT')
 .has('tenantId','tenant-042').has('expiresAtEpoch',lt(1795309200)).drop()
g.V('vertex-1','vertex-2').hasLabel('AuditTrace')
 .has('tenantId','tenant-042').has('createdAtEpoch',lt(1779757200))
 .not(bothE()).drop()

Use explicit IDs, safely serialized query construction and correct timestamp units. Track transaction conflicts in worker telemetry; retry transient conflicts with bounded exponential backoff and jitter. A successful drop response does not itself report exact deleted counts. Classify outcomes and reconcile uncertain commits; do not infer confirmed deletion from absence alone. For exact attribution, design a transactional graph-side audit marker or equivalent mechanism.

Rate fields are initial cluster-wide micro-batches per second, not per-worker rates; tune from the PoC. Enforce concurrency separately. Use conditional claims with expiry/fencing; DynamoDB TransactWriteItems atomically completes a chunk and updates run totals once. 7. Observability: Tracking Discovered vs. Purged Metrics

To provide full operational visibility across all tenants without direct CloudWatch PutMetricData calls (EMF still incurs log and custom metric charges), both the Discovery and Execution Batch containers emit structured JSON logs using the CloudWatch Embedded Metric Format (EMF) under the custom namespace NeptunePurge/MultiTenant.

1. Progress & Delta Metrics

  • RecordsDiscovered (Dimensions: TenantId, EntityType)
  • RecordsPurged (Dimensions: TenantId, EntityType)
  • PurgeCompletionRatio: Dashboard estimate using aligned Sum periods and a nonzero denominator; exact per-run resolved/discovered counts come from ledger. Distinguish confirmed deletes from skipped/absent IDs.
  • RemainingBacklogRecords: Rough queue estimate only: ApproximateNumberOfMessagesVisible * 5000. Exact remaining candidates = sealed manifest totals minus reconciled terminal outcomes, including in-flight and DLQ work.

2. Health, NCU & Throttle Telemetry

  • BatchDeleteLatencyMs (p50, p95, p99)
  • ActiveBatchSize & ActiveWorkerThreads (tracks AIMD adaptation in real time)
  • ObservedWriterNcus vs. ConfiguredMaxPurgeNcu (monitors soft NCU throttle threshold, not guaranteed cost cap)
  • ThrottleBackoffEvents, CircuitBreakerPausedSeconds & ConcurrentModificationRetries

3. Cost & Safety Guardrails

  • Orphan Clone Reaper: A Step Functions Catch path and scheduled reaper reconcile expired clone leases. Verify ownership tags, source/clone IDs, execution status, heartbeat, and expiry; do not delete an active clone merely because it is older than four hours. Delete instance, wait, delete clone cluster, wait; never target production.
  • DLQ Alerting: Configure SQS redrive maxReceiveCount (e.g. 3) and alarm on visible messages in NeptunePurgeChunkDLQ.

Neptune control-plane IAM uses rds: actions even though the SDK service is neptune. Restrict destructive actions to clone resources and verify supported IAM resource types and tag conditions. Include required dependent KMS, service-linked-role and Batch/SFN permissions. Batch job roles and execution roles are separate.

Discovery role: neptune-db:ReadDataViaQuery on the clone resource ID only. Executor: neptune-db:ReadDataViaQuery, neptune-db:DeleteDataViaQuery, and neptune-db:GetQueryStatus as required on the production resource ID. 9.4 Wait helper and clone readiness

wait_for_cluster() {
  local cluster_id="$1" status i
  for ((i=1; i<=120; i++)); do
    status=$(aws neptune describe-db-clusters \
      --db-cluster-identifier "$cluster_id" \
      --query 'DBClusters[0].Status' --output text) || return 1
    echo "Cluster: $cluster_id | Status: $status"
    [[ "$status" == "available" ]] && return 0
    sleep 15
  done
  echo "Timed out waiting for $cluster_id" >&2
  return 1
}

# Before cloning, verify a non-null latest restorable time.
for source in "$PROV_CLUSTER" "$SLS_CLUSTER"; do
  aws neptune describe-db-clusters --db-cluster-identifier "$source" \
    --query 'DBClusters[0].{Status:Status,Latest:LatestRestorableTime,Backup:BackupRetentionPeriod}' \
    --output table
done

Use a bounded DescribeDBClusters polling loop for the cluster; Neptune CLI instance waiters are used for instances. Newly created source clusters must have a usable restorable time. A timeout stops the sequence; it is not permission to create an instance against an unready cluster.

9.8 Remove disposable clones only

Before executing, inspect identifiers, tags, source IDs and cluster membership. Do not substitute a production source identifier. The following example is limited to the two known PoC clones, and assumes one instance per clone.

for clone in "$PROV_CLONE" "$SLS_CLONE"; do
  if [[ "$clone" != neptune-provisioned-clone && "$clone" != neptune-serverless-clone ]]; then
    echo "Refusing unexpected cluster: $clone" >&2
    break
  fi
  aws neptune delete-db-instance \
    --db-instance-identifier "${clone}-writer" --skip-final-snapshot && \
  aws neptune wait db-instance-deleted \
    --db-instance-identifier "${clone}-writer" && \
  aws neptune delete-db-cluster \
    --db-cluster-identifier "$clone" --skip-final-snapshot || break
done

# Verify deletion completes (not merely accepted).
aws neptune describe-db-clusters \
  --query 'DBClusters[].{Cluster:DBClusterIdentifier,Status:Status}' --output table

Poll until the clone is absent; treat only the expected not-found response as successful deletion. Handle dependencies and retries in the runtime orchestrator. Source PoC clusters remain billable until separately removed; this block intentionally does not delete them.
