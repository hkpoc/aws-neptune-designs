1. Architectural Context & Neptune Isolation Mechanics

Purging millions of vertices and edges from live multi-tenant Amazon Neptune clusters (both Provisioned and Neptune Serverless) carries three operational risks: (1) Discovery traversal overhead: deep graph traversals evict warm buffer-cache pages and spike read I/O on production instances. (2) Write amplification & undo-log growth: unthrottled batch drop() mutations flood the writer's request queue and inflate UndoLogListSize, which only the writer can purge. (3) Serverless auto-scaling cost runaway: unthrottled writes push a Serverless cluster up to its configured MaxCapacity (anywhere from 1.0 to 128.0 NCUs).

Neptune Fast Database Clone vs. Read Replica

A Neptune read replica is part of the primary DB cluster and shares its storage volume, so it can't be isolated outside the cluster. For full isolation, the Discovery Phase creates an ephemeral Neptune database clone. It calls RestoreDBClusterToPointInTime with RestoreType=copy-on-write, UseLatestRestorableTime=true, plus explicit VpcSecurityGroupIds, DBSubnetGroupName, DBClusterParameterGroupName and Tags. Then CreateDBInstance adds the clone's single instance. Copy-on-write needs no extra storage at creation; only pages changed later on the source or the clone are copied. The clone has its own compute, buffer cache and endpoints. Limits: same Region, same account, at most 15 clones per copy. Provisioning time isn't published by AWS, so measure it per tenant.

Decoupled Discovery

Zero Prod Impact

Creates an ephemeral single-instance clone per tenant (a fixed Provisioned class, or db.serverless with its own ServerlessV2ScalingConfiguration). Streams candidate vertex and edge IDs with cursor-paginated queries to S3 manifest chunks (JSONL.gz, 5,000 IDs per chunk), checkpointing the cursor so a Spot interruption can resume. Deletes the clone as soon as the scan finishes.

Elastic Scale (Millions to Thousands)

Scale-to-Zero

Handles both the initial multi-million-record backlog (hours to drain) and the lighter weekly runs (minutes). Avoids Lambda's 15-minute timeout and the cost of compute that sits idle between weekly runs.

Hybrid Closed-Loop Execution

Provisioned & Serverless

Sends deletes to the production writer in micro-batches of 100–500 IDs. Polls CloudWatch every 60s (Neptune's 1-minute resolution): CPUUtilization for Provisioned, ServerlessDatabaseCapacity and NCUUtilization for Serverless.

5. Adaptive Database Health & Backpressure Control

Dropping a vertex in Neptune also removes its properties and every incident edge. Large unthrottled deletes cause ConcurrentModificationException conflicts and grow UndoLogListSize. Only the writer purges the undo log, and delete records take longer to purge than other transaction types. On Neptune Serverless, a CPU-only signal falls into an auto-scaling feedback trap: Neptune adds NCUs to absorb the purge load, so CPU stays low while billing climbs toward MaxCapacity.

Serverless Clone & Execution Cost Guardrails
  • Discovery clone compute: attach either a fixed Provisioned instance (for example db.r6g.xlarge) for a hard hourly price ceiling, or db.serverless. For Serverless, pass ServerlessV2ScalingConfiguration={MinCapacity: 2.0, MaxCapacity: 16.0} on the restore call; otherwise the clone inherits the source cluster's range. Values use half-step increments within 1.0–128.0.
  • Execution NCU budget (MaxPurgeNcuThreshold): a per-tenant ceiling, for example 12 NCUs on a cluster whose MaxCapacity is 64. When the writer's instance-level ServerlessDatabaseCapacity reaches the budget, the controller moves to Yellow.
  • Headroom: NCUUtilization already equals current NCUs ÷ the cluster's max NCU setting, so use it alone for headroom (Red above 75%). Read MaxCapacity at runtime from DescribeDBClusters rather than copying it into DynamoDB, where it can drift.
  • Small buffer cache: 1 NCU = 2 GiB RAM, so an instance idling at 2 NCUs has about 4 GiB. AWS's baseline for BufferCacheHitRatio is 99.9%. Below 99%, cap sub-batches at 100–150 IDs.

5.3 Mode-Aware AIMD Controller

60s Polling Loop
// Runs every 60s (Neptune metrics have 1-minute resolution) on a background thread in the Batch executor.
// GetMetricData: Period=60, Stat=Average (Sum for queue/undo); missing datapoints mean 0, since Neptune publishes only non-zero values.
HealthSnapshot snap = pollNeptuneCloudWatchMetrics(writerInstanceId, clusterId);
HealthStatus status = evaluateBaseHealth(
        snap.pendingQueueOrZero(), snap.undoLogSizeOrZero(),
        cmeRetriesLastMinute.get());            // client-side count of ConcurrentModificationException retries

if (tenantConfig.getClusterComputeMode() == ComputeMode.SERVERLESS) {
    // NCUUtilization = current NCUs / cluster max NCU, so it is the single headroom signal
    if (snap.getNcuUtilization() > 75.0) {
        status = HealthStatus.RED;
    } else if (snap.getCurrentNcus() >= tenantConfig.getMaxPurgeNcuThreshold()
            || snap.getNcuUtilization() >= 50.0) {
        status = HealthStatus.maxSeverity(status, HealthStatus.YELLOW);
    }
    if (snap.getBufferCacheHitRatio() < 99.0) {           // AWS baseline: 99.9%
        currentBatchSize = Math.min(currentBatchSize, 150);
        if (snap.getBufferCacheHitRatio() < 95.0) status = HealthStatus.RED;
    }
} else {
    if (snap.getCpuUtilization() > 70.0) {
        status = HealthStatus.RED;
    } else if (snap.getCpuUtilization() >= 45.0) {
        status = HealthStatus.maxSeverity(status, HealthStatus.YELLOW);
    }
}

switch (status) {
    case GREEN -> {
        currentBatchSize = Math.min(maxBatchSize, currentBatchSize + 50);
        activeWorkers    = Math.min(maxWorkers, activeWorkers + 1);
        interBatchDelay  = Math.max(20, interBatchDelay - 25);   // ms
    }
    case YELLOW -> {
        currentBatchSize = Math.max(50, currentBatchSize / 2);
        activeWorkers    = Math.max(1, activeWorkers / 2);
        interBatchDelay  = Math.min(2000, interBatchDelay * 2);
    }
    case RED -> {
        // Extend in-flight message visibility first (ChangeMessageVisibility, max 12h total)
        sqs.extendVisibility(inFlightReceipts, Duration.ofMinutes(5));
        pauseExecutionLoop(Duration.ofSeconds(60));
        emitMetric("CircuitBreakerTripped", 1, tenantId);
    }
}
Day-1 Backlog vs. Weekly Runs

Discovery writes immutable chunks to S3 and enqueues pointers to an SQS queue with MessageRetentionPeriod explicitly set to 1,209,600s (14 days, the maximum; the default is 4 days). A per-tenant MaintenanceWindowMaxMinutes (for example 360) lets the executor stop cleanly when the window closes. If 25M IDs are discovered and only 8M purged in the first window, the remaining 17M stay queued for later nights without re-running discovery, as long as they're drained within 14 days. For larger backlogs, re-enqueue from the S3 manifests (still the source of truth) rather than relying on SQS retention. Set the DLQ retention ≥ the source queue's, since a standard-queue message's expiry is based on its original enqueue time.

7. Observability: Discovered vs. Purged

Both containers write structured JSON logs in CloudWatch Embedded Metric Format (EMF) under the namespace NeptunePurge/MultiTenant. This avoids PutMetricData API calls, but each unique metric and dimension combination is still billed as a custom metric. Keep dimensions to TenantId and EntityType.

1. Progress Metrics

  • RecordsDiscovered, RecordsPurged (TenantId, EntityType)
  • PurgeCompletionRatio = metric math 100 * RecordsPurged / RecordsDiscovered
  • RemainingBacklogRecords ≈ (ApproximateNumberOfMessagesVisible + ApproximateNumberOfMessagesNotVisible) × 5,000. Both SQS metrics are approximate.

2. Health & Throttle Metrics

  • BatchDeleteLatencyMs (p50/p95/p99)
  • ActiveBatchSize, ActiveWorkerThreads
  • ObservedWriterNcus vs. ConfiguredMaxPurgeNcu
  • ThrottleBackoffEvents, CircuitBreakerPausedSeconds, ConcurrentModificationRetries

3. Cost & Safety Guardrails

  • Orphan clone reaper: a Step Functions Catch on every clone path, plus an hourly EventBridge Scheduler → reaper state machine. The reaper deletes clones tagged Purpose=NeptunePurgeDiscovery that are older than 4h (instance first, then cluster). This also keeps you under the limit of 15 clones per copy.
  • DLQ alarm: RedrivePolicy.maxReceiveCount=3 → NeptunePurgeChunkDLQ. Alarm on ApproximateNumberOfMessagesVisible > 0.
  • Alarms on Neptune metrics: TreatMissingData=notBreaching, because Neptune publishes only non-zero values.
