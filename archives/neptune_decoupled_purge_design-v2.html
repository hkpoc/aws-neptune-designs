1. Architectural Context & Neptune Isolation Mechanics

Purging millions of vertices and edges from live multi-tenant Amazon Neptune clusters (both Provisioned and Neptune Serverless) presents three distinct operational risks: (1) Discovery Traverse Overhead, where deep graph traversals evict warm buffer-pool cache pages and spike read IOPS on production instances; (2) Write Amplification & MVCC UndoLog Growth, where unthrottled batch drop() mutations flood the primary writer's transaction queue and inflate UndoLogListSize; and (3) Serverless Auto-Scaling Cost Runaway, where unthrottled writes force Neptune Serverless clusters to scale up to their maximum NCU cap (1 to 128 NCUs).

Critical Neptune Architecture Distinction: Fast Database Clone vs. Read Replica

In Amazon Neptune, a standard Read Replica belongs to the primary DB cluster and shares the underlying distributed storage fleet. Adding a read replica cannot exist "outside the cluster." To achieve true isolation outside the production cluster without incurring full snapshot restore durations or double storage charges, the Discovery Phase provisions an ephemeral Neptune Fast Database Clone (RestoreDBClusterFromDBCluster with copy-tags-to-snapshot). Fast Cloning uses copy-on-write (CoW) page pointers—provisioning in ~5–12 minutes regardless of multi-terabyte storage volume, costing zero extra storage for unchanged pages, and providing 100% compute, buffer cache, and cluster-endpoint isolation from production traffic.

5. Adaptive Database Health & Backpressure Control (Provisioned & Serverless)

Deleting vertices in Amazon Neptune requires removing both the vertex properties and all incident in/out edges. Large unthrottled deletes cause lock contention (ConcurrentModificationException) and grow the MVCC UndoLogListSize, which degrades read latency for production clients. Furthermore, on Neptune Serverless, relying solely on CPUUtilization < 45% causes an auto-scaling feedback trap: Neptune Serverless continuously scales up NCUs (up to 128 NCUs) to absorb the purge load, keeping CPU artificially low while silently driving your NCU-second billing to MaxCapacity.

Neptune Serverless Discovery Clone & Execution Cost Guardrails
  • Discovery Clone Compute Strategy: Even when a tenant's production cluster runs on Neptune Serverless, you can attach either a fixed Provisioned instance (e.g., db.r6g.xlarge) for a hard hourly price ceiling during full-throttle scans, or a capped db.serverless instance configured with MinCapacity=2.0, MaxCapacity=16.0 so the discovery scan never scales beyond 16 NCUs.
  • Execution NCU Soft Cap (MaxPurgeNcuThreshold): On the production Serverless Writer, the Execution Worker enforces a per-tenant NCU budget ceiling (e.g., 12 NCUs on a cluster whose daytime MaxCapacity is 64 NCUs). Once ServerlessDatabaseCapacity reaches MaxPurgeNcuThreshold, the AIMD controller shifts into the Yellow (Throttle) state to hold NCU allocation steady.
  • Small Buffer-Cache Protection: Because 1 NCU ≈ 2 GB RAM, a Serverless instance idling at 2 NCUs overnight has only ~4 GB of buffer cache. If BufferCacheHitRatio dips below 90%, the worker caps sub-batch sizes at 100–150 IDs to prevent storage I/O thrashing.

5.3 Mode-Aware AIMD Backpressure Controller (Execution Worker Logic)

30s Polling Loop 
// Executed every 30s by background health-monitor thread in AWS Batch Executor
HealthSnapshot snap = pollNeptuneCloudWatchMetrics(tenantConfig.getSourceClusterId());
HealthStatus status = evaluateBaseHealth(snap.getPendingQueue(), snap.getUndoLogSize(), snap.getCmeCount());

if (tenantConfig.getClusterComputeMode() == ComputeMode.SERVERLESS) {
    // Enforce NCU cost budget ceiling & NCU utilization thresholds
    if (snap.getCurrentNcus() >= tenantConfig.getClusterMaxNcu() * 0.85 || snap.getNcuUtilization() > 75.0) {
        status = HealthStatus.RED;
    } else if (snap.getCurrentNcus() >= tenantConfig.getMaxPurgeNcuThreshold() || snap.getNcuUtilization() >= 50.0) {
        status = HealthStatus.maxSeverity(status, HealthStatus.YELLOW);
    }
    // Protect small low-NCU buffer caches from storage I/O thrashing
    if (snap.getBufferCacheHitRatio() < 90.0) {
        currentBatchSize = Math.min(currentBatchSize, 125);
    }
} else {
    // Provisioned instance CPU evaluation
    if (snap.getCpuUtilization() > 70.0) {
        status = HealthStatus.RED;
    } else if (snap.getCpuUtilization() >= 45.0) {
        status = HealthStatus.maxSeverity(status, HealthStatus.YELLOW);
    }
}

// Apply Additive-Increase / Multiplicative-Decrease (AIMD)
if (status == HealthStatus.GREEN) {
    currentBatchSize = Math.min(maxBatchSize, currentBatchSize + 50);
    activeWorkers    = Math.min(maxWorkers, activeWorkers + 1);
    interBatchDelay  = Math.max(20, interBatchDelay - 25); // ms
} else if (status == HealthStatus.YELLOW) {
    currentBatchSize = Math.max(50, currentBatchSize / 2);
    activeWorkers    = Math.max(1, activeWorkers / 2);
    interBatchDelay  = Math.min(2000, interBatchDelay * 2);
} else if (status == HealthStatus.RED) {
    pauseExecutionLoop(Duration.ofSeconds(60)); // Keep SQS visibility lease heartbeated
    emitMetric("CircuitBreakerTripped", 1, tenantId);
}
Handling the Day-1 Multi-Million Backlog vs. Ongoing Weekly Runs

Because Discovery writes immutable manifest chunks to S3 and enqueues pointers into SQS (with a 14-day retention period), you can safely configure a Max Execution Window per tenant in DynamoDB (e.g., 6 hours during Sunday off-peak). If the Day-1 backlog discovers 25 million records and only 8 million are purged within the Sunday off-peak window while maintaining CPUUtilization < 50% (or ServerlessDatabaseCapacity ≤ 12 NCUs), the worker cleanly exits when the maintenance window closes. The remaining 17 million IDs remain safely queued in SQS/S3 and can be drained on subsequent nights without re-running Discovery.

7. Observability: Tracking Discovered vs. Purged Metrics

To provide full operational visibility across all tenants without incurring high CloudWatch PutMetricData API bills, both the Discovery and Execution Batch containers emit structured JSON logs using the CloudWatch Embedded Metric Format (EMF) under the custom namespace NeptunePurge/MultiTenant.

1. Progress & Delta Metrics

  • RecordsDiscovered (Dimensions: TenantId, EntityType)
  • RecordsPurged (Dimensions: TenantId, EntityType)
  • PurgeCompletionRatio: Calculated via Metric Math (RecordsPurged / RecordsDiscovered) * 100
  • RemainingBacklogRecords: Tracked via SQS ApproximateNumberOfMessagesVisible * 5000

2. Health, NCU & Throttle Telemetry

  • BatchDeleteLatencyMs (p50, p95, p99)
  • ActiveBatchSize & ActiveWorkerThreads (tracks AIMD adaptation in real time)
  • ObservedWriterNcus vs. ConfiguredMaxPurgeNcu (verifies Serverless NCU cap compliance)
  • ThrottleBackoffEvents, CircuitBreakerPausedSeconds & ConcurrentModificationRetries

3. Cost & Safety Guardrails

  • Orphan Clone Reaper: A Step Functions Catch block + fallback EventBridge rule ensures any clone tagged Purpose=NeptunePurgeDiscovery older than 4 hours is force-deleted.
  • DLQ Alerting: CloudWatch Alarm triggers if any chunk fails 3 times and lands in NeptunePurgeChunkDLQ.
