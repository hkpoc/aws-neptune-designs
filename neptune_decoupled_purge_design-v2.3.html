What changed in v2.3: per-tenant KMS keys and soft-delete edge purge

Some tenants encrypt their resources with their own customer managed KMS key, and some of those keys use imported (BYOK) key material. v2.3 supports this with the following deployment assumptions:

  • Edges only, soft-deleted only: the engine drops only edges whose soft-delete property is isDeleted=true, and re-checks that property in the same query that drops the edge. Vertices are never dropped. Timestamp and retention rules, the vertex phase, the edge/vertex barrier and the vertex queue are removed.
  • One account: tenant clusters, tenant keys and the purge engine all live in the same AWS account and Region. Neptune doesn't support cross-account cloning, so this assumption is required.
  • Tenant keys mean dedicated clusters: a tenant with its own key (EncryptionMode=TENANT_KEY) always has its own cluster. Shared clusters use the platform key (PLATFORM_KEY).
  • Tenant-scoped data: S3 manifests, checkpoints and Athena results are encrypted with the tenant's key. SQS, DynamoDB, CloudWatch Logs and Step Functions hold only anonymized element IDs, counts and references, so they use the platform key.

1. Architectural Context & Neptune Isolation Mechanics

Purging millions of soft-deleted edges from live multi-tenant Amazon Neptune clusters (both Provisioned and Neptune Serverless) carries three operational risks (the engine drops only edges marked isDeleted=true and never drops vertices): (1) Discovery traversal overhead: deep graph traversals evict warm buffer-cache pages and spike read I/O on production instances. (2) Write amplification & undo-log growth: unthrottled batch drop() mutations flood the writer's request queue and inflate UndoLogListSize, which only the writer can purge. (3) Serverless auto-scaling cost runaway: unthrottled writes push a Serverless cluster up to its configured MaxCapacity (anywhere from 1.0 to 128.0 NCUs).

Neptune Fast Database Clone vs. Read Replica

A Neptune read replica is part of the primary DB cluster and shares its storage volume, so it can't be isolated outside the cluster. For full isolation, the Discovery Phase creates an ephemeral Neptune database clone. It calls RestoreDBClusterToPointInTime with RestoreType=copy-on-write, UseLatestRestorableTime=true, EnableIAMDatabaseAuthentication=true, plus explicit VpcSecurityGroupIds, DBSubnetGroupName, DBClusterParameterGroupName and Tags. Then CreateDBInstance adds the clone's single instance. Copy-on-write needs no extra storage at creation; only pages changed later on the source or the clone are copied. The clone has its own compute, buffer cache and endpoints. The restore omits KmsKeyId, so the clone is encrypted with the source cluster's key and stays inside the tenant's encryption boundary (section 6). Limits: same Region, same account (cross-account cloning isn't supported), at most 15 clones per copy. Provisioning time isn't published by AWS, so measure it per tenant.

Clone preflight, security and scope
  • Preflight: confirm the source cluster is available and its LatestRestorableTime is non-null (new clusters may not have one yet). If the check fails, fail the run. Never fall back to a full-copy restore: omitting RestoreType defaults to full-copy.
  • Key preflight: confirm the cluster's KmsKeyId matches the configured key, the key is Enabled, and BYOK key material stays valid for the whole run. If any check fails, don't create a clone (section 6.2).
  • IAM authentication: the restore call defaults EnableIAMDatabaseAuthentication to false, so always pass true. The clone security group allows port 8182 only from the discovery worker security group.
  • Least privilege: the discovery job role has only neptune-db:ReadDataViaQuery and never holds delete rights. The executor role has ReadDataViaQuery, DeleteDataViaQuery and GetQueryStatus, scoped to the production cluster resource ID. Both jobs reach S3 and the tenant's key only through a tenant-tagged session (section 6.3).
  • Tenant scope: a clone contains the entire source cluster. When tenants share a cluster (only possible with PLATFORM_KEY), every discovery query and every production delete filters on the tenant property.
  • Authority: the clone produces candidates, not delete decisions. Every delete is revalidated against live production (section 5.4).

Decoupled Discovery

Zero Prod Impact

Creates an ephemeral single-instance clone per tenant (a fixed Provisioned class, or db.serverless with its own ServerlessV2ScalingConfiguration). Streams the IDs of tenant-filtered edges with isDeleted=true with cursor-paginated queries to S3 manifest chunks (JSONL.gz, 5,000 IDs per chunk), checkpointing the cursor so a Spot interruption can resume. Deletes the clone as soon as the scan finishes.

Elastic Scale (Millions to Thousands)

Scale-to-Zero

Handles both the initial multi-million-record backlog (hours to drain) and the lighter weekly runs (minutes). Avoids Lambda's 15-minute timeout and the cost of compute that sits idle between weekly runs.

Hybrid Closed-Loop Execution

Provisioned & Serverless

Sends revalidated, conditional deletes to the production writer in micro-batches of 100–500 IDs, under one rate limiter per source cluster. Polls CloudWatch every 60s (Neptune's 1-minute resolution): CPUUtilization for Provisioned, ServerlessDatabaseCapacity and NCUUtilization for Serverless.

4.1 Runtime Lifecycle Contract

Authoritative
  1. Lease and freeze. Acquire a fenced lease on the source cluster (keyed by cluster resource ID) and a tenant run lease in DynamoDB: conditional put, expiry and heartbeat. Record the rule version (soft-delete property and value) and the resolved KMS key ARN in the run ledger. All later steps use these frozen values.
  2. Key check. Run the key preflight in 6.2, both before resuming a paused run and before starting a new discovery. If the key isn't usable, start nothing: record a SkipReason and raise the per-tenant key alarm.
  3. Resume before discover. If the tenant has a PAUSED run, resume it from its sealed manifest and chunk ledger first. Rebuild any expired SQS pointers. Start a new discovery only once nothing is outstanding.
  4. Clone. Run the preflight, then restore, poll, create the instance and poll. Verify the clone's endpoint, CloneGroupId, IAM authentication, and that StorageEncrypted=true with the same KmsKeyId as the source, before running discovery.
  5. Discover and seal. Scan with tenant filters and checkpoint the cursor. Write deterministic edge chunks (EDGE-000001…) to S3, each encrypted with an explicit SSEKMSKeyId (6.1), and record them in the chunk ledger. Seal the manifest (chunk counts plus a _SEALED object) only after the full scan, then publish SQS pointers. An executor never starts on an unsealed manifest.
  6. Tear down the clone. On success or failure (Catch): delete the instance, wait, delete the cluster with SkipFinalSnapshot=true, wait. Persist the cleanup status. The reaper handles aborted executions.
  7. Execute (single phase). Executors drain the edge chunk queue. There's no vertex phase and no barrier. A chunk's SQS message is deleted only after its ledger commit.
  8. Window close. Checkpoint, release the leases and mark the run PAUSED.
  9. Key lost mid-run. If a KMS error shows the tenant key is unusable, stop new writes, mark in-flight batches Uncertain, tear down the clone, release the leases, and mark the run FAILED with FailureReason=TENANT_KEY_UNAVAILABLE. Never retry it automatically (6.2).
  10. Complete. Mark the run COMPLETED only when every chunk is terminal (DLQ chunks resolved, uncertain outcomes reconciled) and clone cleanup is confirmed.

5. Adaptive Database Health & Backpressure Control

Dropping an edge removes the edge and its properties only. Vertices are never dropped, even when a vertex is left with no edges. Large unthrottled deletes cause ConcurrentModificationException conflicts and grow UndoLogListSize. Only the writer purges the undo log, and delete records take longer to purge than other transaction types. On Neptune Serverless, a CPU-only signal falls into an auto-scaling feedback trap: Neptune adds NCUs to absorb the purge load, so CPU stays low while billing climbs toward MaxCapacity.

Serverless Clone & Execution Cost Guardrails
  • Discovery clone compute: attach either a fixed Provisioned instance (for example db.r6g.xlarge) for a hard hourly price ceiling, or db.serverless. For Serverless, pass ServerlessV2ScalingConfiguration={MinCapacity: 2.0, MaxCapacity: 16.0} on the restore call; otherwise the clone inherits the source cluster's range. Values use half-step increments within 1.0–128.0.
  • Execution NCU budget (MaxPurgeNcuThreshold): a per-cluster soft threshold shared by all tenants on that writer, for example 12 NCUs on a cluster whose MaxCapacity is 64. When the writer's instance-level ServerlessDatabaseCapacity reaches it, the controller moves to Yellow. This reduces purge pressure but isn't a cost cap: application traffic can still raise NCUs.
  • Headroom: NCUUtilization already equals current NCUs ÷ the cluster's max NCU setting, so use it alone for headroom (Red above 75%). Read MaxCapacity at runtime from DescribeDBClusters rather than copying it into DynamoDB, where it can drift.
  • Small buffer cache: 1 NCU = 2 GiB RAM, so an instance idling at 2 NCUs has about 4 GiB. AWS's baseline for BufferCacheHitRatio is 99.9%. Below 99%, cap sub-batches at 100–150 IDs.

// rate budget through a DynamoDB lease item (ClusterResourceId) with a fencing token and heartbeat.
// Cadence: CloudWatch every 60s (1-minute resolution), live query status every 15s, latency and CME every batch.

writer = resolveCurrentWriter(clusterId);          // DescribeDBClusters → DBClusterMembers[IsClusterWriter]
HealthStatus status = GREEN;
if (!writer.id.equals(lastWriterId)) {             // failover or replacement
    status = RED;                                  // reconnect via cluster endpoint, re-baseline
    lastWriterId = writer.id;
}
cw     = getMetricData(writer.id, clusterId, 60);  // AWS/Neptune, DBInstanceIdentifier = current writer
live   = getQueryStatus(clusterEndpoint);          // neptune-db:GetQueryStatus
policy = loadClusterThrottlePolicy(clusterId);

if (cw.cpu.isMissingOrOlderThan(Duration.ofMinutes(3))) status = RED;  // always published: missing = stale
long pending  = cw.pendingQueue.orElse(0L);        // published only when non-zero
long undoLog  = cw.undoLog.orElse(0L);             // published only when non-zero
long queued   = live.acceptedQueryCount - live.runningQueryCount;

status = maxSeverity(status,
        band(cw.cpu.get(),            policy.CpuThrottleThresholdPct,  policy.MaxCpuThresholdPct),
        band(max(pending, queued),    1,                               policy.MaxPendingQueueDepth),
        band(undoLog,                 policy.UndoLogThrottleThreshold, policy.MaxUndoLogSize),
        band(cmeRetriesLastMinute(),  1,                               policy.MaxConflictRetriesPerMinute),
        band(appP95LatencyMs(),       0.8 * policy.AppP95SloMs,        policy.AppP95SloMs));

if (writer.isServerless()) {
    status = maxSeverity(status,
            band(cw.ncuUtilization, policy.NcuUtilizationThrottleThresholdPct, policy.MaxNcuUtilizationPct),
            cw.currentNcus >= policy.MaxPurgeNcuThreshold ? YELLOW : GREEN,
            cw.bufferCacheHitRatio < policy.StopBufferCacheHitRatioPct ? RED : GREEN);
}

// AIMD on ONE control variable: cluster-wide micro-batches per second
switch (status) {
    case GREEN -> {
        if (++greenStreak >= policy.GreenSamplesToIncrease)
            rate = Math.min(policy.MaxRate, rate + policy.RateIncreaseStep);
    }
    case YELLOW -> { greenStreak = 0; rate = Math.max(policy.MinRate, rate / 2); }
    case RED -> {
        greenStreak = 0;
        pauseNewWrites();                                    // let in-flight batches finish
        sqs.extendVisibility(inFlightReceipts, Duration.ofMinutes(5));   // capped at 12h from receipt
        emitMetric("CircuitBreakerTripped", 1, clusterId);
        waitForFreshGreenSamples(policy.GreenSamplesToIncrease);
    }
}

// Batch size is bounded separately; AIMD does not adapt it
batchSize = policy.MaxBatchSize;                                       // edge drops: no degree-aware sizing needed
if (writer.isServerless() && cw.bufferCacheHitRatio < policy.MinBufferCacheHitRatioPct)
    batchSize = Math.min(batchSize, 150);
Day-1 Backlog vs. Weekly Runs

Discovery writes immutable chunks to S3 and enqueues pointers to an SQS queue with MessageRetentionPeriod explicitly set to 1,209,600s (14 days, the maximum; the default is 4 days). A per-tenant MaintenanceWindowMaxMinutes (for example 360) lets the executor stop cleanly when the window closes. If 25M IDs are discovered and only 8M purged in the first window, the executor checkpoints, releases its leases and marks the run PAUSED, never COMPLETED. The remaining 17M stay in the sealed S3 manifests and the chunk ledger. The next window resumes them before any new discovery and revalidates every candidate against production (5.4). SQS pointers older than 14 days expire, so the resume step rebuilds missing pointers from the manifest and chunk ledger rather than trusting queue depth. Set the DLQ retention ≥ the source queue's, since a standard-queue message's expiry is based on its original enqueue time.

5.4 Live-Data Correctness: Revalidate Before Delete

Safety

The clone is a point-in-time candidate list, not authority to delete. Between the snapshot and the delete, an edge can be restored (isDeleted set back to false), reassigned or removed by someone else. Every production drop therefore re-checks isDeleted=true and the tenant in the same query, so an edge restored after discovery is never dropped.

// Discovery (on the clone, streamed with a cursor):
//      g.E().has('tenantId', T).has('isDeleted', true).id()

// 1. Classify (read on the current writer, per micro-batch):
//      present  = g.E(ids).id()
//      eligible = g.E(ids).has('tenantId', T).has('isDeleted', true).id()
// 2. Conditional drop: the soft-delete check is in the same traversal, so an edge
//    restored (isDeleted=false) after step 1 is never dropped.
g.E('edge-1', 'edge-2')
 .has('tenantId', 'tenant-042')
 .has('isDeleted', true)                        // only soft-deleted edges
 .drop()                                        // edges only: never g.V(...).drop()

// 3. Uncertain outcome (timeout or connection loss after send): re-read g.E(eligible).id() before retrying.
  • Outcomes per ID: ConfirmedDeleted, AlreadyAbsent, NoLongerEligible, Uncertain or Failed. drop() doesn't return counts, so counts come from the classify step plus confirmation, never from the absence of an error alone.
  • Vertices are out of scope. The executor only builds g.E(...) traversals, and a startup guard rejects any rule whose EntityType isn't EDGE. Vertices left with no edges stay in place.
  • Restored edges: an edge whose isDeleted went back to false after discovery is counted as NoLongerEligible and left untouched.
  • Query construction: pass IDs and values through driver bytecode or parameter binding, never string concatenation. The soft-delete property name is case-sensitive and must match the stored key exactly (SoftDeleteProperty, e.g. isDeleted). The value must match the stored type: has('isDeleted', true) doesn't match the string "true". Check one tenant's data before enabling it.
  • Conflicts: retry ConcurrentModificationException with bounded exponential backoff and jitter, and count retries in ConcurrentModificationRetries. On ReadOnlyViolationException (writer moved), reconnect to the cluster endpoint, mark the in-flight batch Uncertain and resolve it.

6. Per-Tenant Encryption Boundary (KMS & BYOK)

Each tenant has one of two encryption modes, set in TenantConfig. TENANT_KEY: the tenant has a dedicated cluster encrypted with its own customer managed key, which may use imported (BYOK) key material. PLATFORM_KEY: the cluster is shared, or dedicated without a tenant key, and uses the platform key. A TENANT_KEY tenant never shares a cluster, because a Neptune cluster has exactly one storage key and that key can't be changed after creation. Whether the key is BYOK is read from DescribeKey (Origin=EXTERNAL) at run time, not stored in config.

Losing the key permanently breaks the cluster

AWS: if Neptune loses access to a cluster's encryption key, for example because access was revoked, the cluster is placed into a terminal state and can only be restored from a backup. This also applies to the discovery clone. For BYOK tenants, deleting the key material, letting it expire, or disabling the key all have this effect. The purge engine therefore checks the key before it creates anything, treats key loss mid-run as a permanent failure (not a pause), and never retries automatically.

6.3 IAM, key policy and S3 enforcement

Tenant-Tagged Sessions

Batch can't override a job role per job, so both job roles hold only Neptune data-plane rights plus sts:AssumeRole/sts:TagSession on neptune-purge-tenant-data. When a container starts, it assumes that role with session tags TenantId and TenantKmsKeyArn, taken from job parameters set by Step Functions from TenantConfig. All S3 and KMS access uses that session. Role chaining caps the session at 1 hour, so containers use an auto-refreshing STS credentials provider with the same tags.

  • Executor deletes need no KMS access. Neptune data-plane queries are authorized by IAM database authentication. The cluster uses its own grant to decrypt.
  • Session tags protect against mistakes, not against compromised code. The job picks its own tags from its input, so tagging stops cross-tenant bugs but not a malicious container. If a BYOK tenant contractually requires a hard role boundary, register a per-tenant job definition with a per-tenant job role (same policies with fixed values instead of tags).
  • Key policy ownership: statements (a) are added when the tenant's key is onboarded and checked by IaC drift detection. Without them, the restore fails with a KMS access error, which the preflight reports as KEY_MISMATCH/TENANT_KEY_UNAVAILABLE rather than as a generic failure.
  • Reaper: deleting a clone needs no KMS access. Deleting it retires its grant.

6.4 Data classification for platform-key stores

Rule

SQS, DynamoDB, CloudWatch Logs and Step Functions are shared across tenants and use the platform key. That's acceptable only because they never hold customer data:

  • Allowed: tenant ID, run ID, chunk ID, S3 object keys, counts, run timestamps, rule versions, and anonymized element IDs (for example LastCursor).
  • Never allowed: property values, manifest lines, or raw query text. Sanitize Neptune driver exceptions (which can echo predicates and IDs) before logging, and keep only the error code and a request ID.
  • Guardrail: TenantConfig.ElementIdsAnonymized must be true for the cursor to live in DynamoDB. If a tenant's element IDs are natural keys, the cursor moves to s3://…/{tenant}/{run}/_cursor.json under the tenant key, and DynamoDB stores only that S3 key.

  • Claim: a chunk is claimed with a conditional update (Status = PENDING, or a CLAIMED lease that has expired) that increments LeaseVersion. Writes from a holder with a stale token are rejected.
  • Complete: TransactWriteItems sets the chunk to COMPLETED and adds its outcome counts to the run ledger in one transaction. The condition Status <> COMPLETED prevents double counting when SQS redelivers the message (delivery is at-least-once).

  • Pointer rebuild: rebuild expired or missing SQS pointers from the sealed manifest plus the chunk ledger, never from queue depth.

8. Observability: Discovered vs. Purged

Both containers write structured JSON logs in CloudWatch Embedded Metric Format (EMF) under the namespace NeptunePurge/MultiTenant. This avoids PutMetricData API calls, but each unique metric and dimension combination is still billed as a custom metric. Keep dimensions to TenantId (every purged record is an edge).

1. Progress Metrics

  • RecordsDiscovered, RecordsDeleted, RecordsAlreadyAbsent, RecordsNoLongerEligible, RecordsUncertain (TenantId)
  • PurgeCompletionRatio: a dashboard estimate from metric math over aligned periods. Exact per-run figures come from the run ledger: (Deleted + AlreadyAbsent + NoLongerEligible) ÷ Discovered.
  • RemainingBacklogRecords ≈ (ApproximateNumberOfMessagesVisible + ApproximateNumberOfMessagesNotVisible) × 5,000. Both SQS metrics are approximate. The exact backlog is the sealed manifest totals minus terminal outcomes in the chunk ledger.

2. Health & Throttle Metrics

  • BatchDeleteLatencyMs (p50/p95/p99)
  • ActiveBatchSize, ActiveWorkerThreads
  • ObservedWriterNcus vs. ConfiguredMaxPurgeNcu
  • ThrottleBackoffEvents, CircuitBreakerPausedSeconds, ConcurrentModificationRetries

3. Cost & Safety Guardrails

  • Orphan clone reaper: a Step Functions Catch on every clone path, plus an hourly EventBridge Scheduler → reaper state machine. The reaper deletes a clone only when all three hold: (a) it carries Purpose=NeptunePurgeDiscovery, RunId and SourceClusterId tags; (b) the owning execution is no longer RUNNING or its run-lease heartbeat has expired; (c) its identifier matches the clone naming pattern. Age alone is never enough, because discovery can legitimately run up to its 6h job timeout. It deletes the instance, waits, then deletes the cluster with SkipFinalSnapshot. This also keeps you under the limit of 15 clones per copy. A clone in inaccessible-encryption-credentials (tenant key lost) is still deleted. If the delete is rejected, the reaper emits CloneStuckKeyUnavailable for manual action.
  • Tenant key alarms (v2.3): TenantKeyUnavailable (TenantId) on any key-related skip or failure. KeyMaterialHoursRemaining for BYOK keys with expiring material, with an alarm below 2× MinKeyMaterialValidityHours. KeyMismatch when config drift is detected. These go to the tenant-operations channel, separately from purge health, because key loss affects the production cluster as well.
  • DLQ alarm: RedrivePolicy.maxReceiveCount=3 → NeptunePurgeChunkDLQ. Alarm on ApproximateNumberOfMessagesVisible > 0.
  • Stale telemetry: the executor stops new writes when writer CPUUtilization has been missing for 3 minutes or the writer instance changes. Alarm on CircuitBreakerPausedSeconds.
  • Alarms on Neptune metrics: TreatMissingData=notBreaching, because Neptune publishes only non-zero values.
